# main 分支 Python 维护版静态审查问题汇总

本汇总针对 `HXwHSJS/ba-keysmith` 仓库 `main` 分支的原有 Python 维护版，不对标 C# / next 重构线。审查重点是：现有 Python/Tkinter 架构下的最小维护修复、输入拦截边界、宏停止可靠性、配置兼容性、打包发布稳定性，以及不破坏已有用户配置的改法。当前 main 分支已经有明显维护进展：`mapper.py` 已经引入 `is_game_window_foreground()`，`_is_game_active()` 不再只判断 `BlueArchive.exe` 进程存在，而是要求进程存在并且前台窗口匹配；`utils.py` 中也通过 `GetForegroundWindow()`、`GetWindowThreadProcessId()`、`psutil.Process(pid).name()` 判断前台进程名；`_stop_lock` 已经从布尔值改成 `threading.Lock()`，并新增 `_macro_lock`；GUI 也增加了多配置方案、运行态热更新和热更新失败恢复旧映射逻辑。这些方向是正确的。但当前维护版仍未完全闭合关键风险，主要问题如下。

## P0：确认并修复 `suppress=True` 在非游戏窗口下可能吞键的问题

当前 `KeyMapper` 已经加入前台窗口判断，这是正确方向。但 hook 注册仍然使用 `suppress=True`，包括普通键、成对键以及 scan-code 方式处理的 Alt 键。例如 `keyboard.hook_key(..., suppress=True)`、`keyboard.on_press_key(..., suppress=True)`、`keyboard.on_release_key(..., suppress=True)`。handler 内部在非运行、禁用、非游戏前台时会 `return True`，意图是放行原始输入；但需要确认 `keyboard` 库在 `suppress=True` 时，是否会根据 callback 返回值动态决定放行，还是注册级别无条件吞掉触发键。如果 `suppress=True` 是注册级阻断，那么即使 handler 返回 `True`，游戏不在前台时，用户在浏览器、聊天框、编辑器、记事本里按到映射触发键，也可能被 BAKS 吞掉。也就是说，当前代码已经修了“不要在非游戏前台发送映射输入”，但可能还没修掉“不要在非游戏前台吞掉原始按键”。需要先写一个最小验证脚本确认行为：`import keyboard; def cb(e): print(e.name, e.event_type); return True; keyboard.hook_key("q", cb, suppress=True); keyboard.wait("esc")`，然后在记事本里按 `q`。如果记事本没有输入 `q`，说明当前架构仍存在 P0 问题。修复策略建议三选一：第一，非游戏前台时不安装 suppress hook；第二，仅在 BlueArchive.exe 前台时安装 suppress hook，离开游戏窗口时卸载；第三，改为非 suppress 监听，再只在游戏前台时执行映射逻辑。目标是：游戏不在前台时，BAKS 既不发送映射输入，也不吞掉用户在其他窗口中的原始输入。

## P1：前台窗口检测缓存时间过长，Alt-Tab 后可能短时间误判

当前前台判断有两层缓存：`utils.py` 中 `is_game_window_foreground()` 存在 `FOREGROUND_CHECK_INTERVAL = 0.3`，`mapper.py` 中 `_is_game_active()` 又有 `_game_check_interval = 0.5`。进程存在性缓存可以接受，但前台窗口是输入工具的安全边界，不适合使用这么长的缓存。用户从游戏 Alt-Tab 到聊天框、浏览器或编辑器后，0.3 到 0.5 秒内仍可能被认为游戏处于前台，从而导致按键映射或吞键边界出现延迟。维护版建议：进程存在性可以继续缓存 0.5 秒；前台窗口判断应实时检查，或者最多缓存 30–50ms；尤其在 `event_type == "down"` 时应强制实时调用前台窗口判断，不要走长缓存。目标是：切出游戏后立即停止映射输入与按键拦截，不给错误窗口发送或吞掉输入。

## P1：`stop()` 清空宏 stop flag，未退出宏线程可能继续运行

当前 `stop()` 调用 `stop_active_macros()` 后，会在 `_macro_lock` 内直接清空 `_macro_threads` 和 `_macro_stop_flags`。如果某个宏线程没有在 `join_timeout=0.5` 内退出，stop flag 被清空后，该线程后续读取 `_macro_stop_flags.get(trigger, False)` 会得到 `False`，理论上可能继续执行。这个问题在无限循环宏、长等待宏、鼠标拖拽宏、组合键宏中风险更高。建议不要在 `stop()` 中直接清空仍活跃的宏线程状态；只清理已经退出的线程；最好把 `_macro_stop_flags` 从普通 bool 字典改成 `threading.Event` 字典，例如 `_macro_stop_events[trigger].set()`，宏线程检查 `event.is_set()`。stop flag / stop event 的生命周期应由宏线程自己的 `finally` 阶段清理，而不是由 `stop()` 抢先清理。最小修法是：`stop()` 调用 `stop_active_macros()` 后，只遍历 `_macro_threads`，对 `not thread.is_alive()` 的项做 pop；仍 alive 的线程保留 stop flag。目标是：停止映射后，所有宏都能可靠终止，不会因为状态被提前清空而残留继续执行。

## P1：新建/重命名配置方案对话框存在重复恢复运行状态风险

`create_new_config()` 和 `rename_current_config()` 中，如果 mapper 正在运行，会调用 `_pause_mapper_for_dialog()` 暂停运行态。当前对话框关闭协议里会执行 `restore_mapper()` 再 `dialog.destroy()`，但 `self.root.wait_window(dialog)` 返回后又会再次调用 `restore_mapper()`。而且当前 `restore_mapper()` 传入的是动态的 `self._dialog_pause_depth`，不是 `_pause_mapper_for_dialog()` 返回时固定的 token。重复恢复可能导致 `_dialog_pause_depth`、`_dialog_pause_previous_enabled` 状态异常，极端情况下可能把 `mapper.enabled` 设置成 `None`，进而让运行/暂停状态显示和真实状态不一致。建议使用一次性 guard：`pause_token = self._pause_mapper_for_dialog(); restored = False; def restore_once(): nonlocal restored; if restored: return; restored = True; self._restore_mapper_after_dialog(pause_token)`。关闭窗口协议和 `wait_window()` 后都只调用 `restore_once()`。同时 `_restore_mapper_after_dialog()` 应接受 `_pause_mapper_for_dialog()` 返回的固定 token，而不是当前动态 depth。目标是：打开/关闭新建配置、重命名配置等对话框后，mapper 的运行/暂停状态恢复准确，不出现状态错乱。

## P1：配置方案名称未净化，可能生成非法路径或路径穿越

当前多配置方案使用 `config_name_to_filename(name)` 直接拼接文件名：`config_{name}.json`。GUI 侧只做了 `strip()` 和重名检查，没有过滤 `/`、`\`、`..`、冒号、星号、问号、双引号、尖括号、竖线等非法或路径字符。用户输入包含这些字符时，可能生成非法文件名、子目录路径，甚至逃出 `%APPDATA%\BAKeySmith` 配置目录。这虽然是本地工具，但仍属于配置文件管理的维护风险。建议增加统一校验函数并在 `create_config()`、`rename_config_file()`、GUI 新建配置方案、GUI 重命名配置方案中统一调用。建议规则：配置名不能为空；不能是 `.` 或 `..`；不能包含 `..` 路径跳转；不能包含 `\ / : * ? " < > |`；可选地限制长度，例如 1–64 个字符。参考实现：`INVALID_CONFIG_NAME_CHARS = set('\\/:*?"<>|')`；`def validate_config_name(name): name = (name or "").strip(); if not name: raise ValueError("配置名称不能为空"); if name in (".", "..") or ".." in name: raise ValueError("配置名称不能包含路径跳转"); if any(ch in INVALID_CONFIG_NAME_CHARS for ch in name): raise ValueError('配置名称不能包含 \\ / : * ? " < > |'); return name`。目标是：配置文件始终只能创建在 `%APPDATA%\BAKeySmith` 内部，不允许用户输入影响路径结构。

## P2：README 与脚本编译器关于 `wait` 小数支持不一致

README 中写明 `wait <毫秒>` 支持小数，但 `ScriptCompiler` 中实际使用 `ms = int(args[0])`，因此 `wait 50.5` 会编译失败。这是典型的文档与实现不一致。维护版二选一即可：要么把编译器改成 `ms = float(args[0])`，并继续保留 README 的“小数支持”；要么把 README 改成“不支持小数”。建议支持 float，因为执行器 `_precise_wait()` 本身按毫秒计算，能够处理小数等待。额外建议增加范围限制，例如 `0 <= wait <= 600000`，避免用户误填超大等待值导致宏长时间难以停止。目标是：文档行为和实际编译器行为一致，用户按 README 写脚本不会失败。

## P2：宏编辑器实时语法检查缺少 debounce，快速输入时可能堆积任务

`MacroEditorDialog.on_key_release()` 每次按键都会调用 `self.top.after(300, self.check_syntax)`，但没有保存 after id，也没有取消上一次 pending 的 after 任务。用户快速输入时，会堆积多个延迟语法检查任务，脚本稍大时可能导致 GUI 抖动、卡顿或状态栏反复刷新。建议增加 debounce：初始化 `self._syntax_after_id = None`；新增 `schedule_syntax_check()`，如果已有 `_syntax_after_id`，先 `after_cancel()`，再重新 `after(300, self.check_syntax)`；`check_syntax()` 执行开始或结束时将 `_syntax_after_id = None`。目标是：宏编辑器输入流畅，语法检查只在用户停止输入一小段时间后执行一次，不堆积任务。

## P2：宏编辑器允许保存语法错误脚本，运行态会在后续编译失败

当前宏脚本存在语法错误时，保存前会弹窗询问，但用户确认后仍可以保存错误脚本。保存后，运行态 `replace_mappings()` 或启动 mapper 时会重新编译，可能导致热更新失败或下次启动映射失败。这会让“配置文件能保存，但不能运行”的状态变得常见。维护版建议默认禁止保存语法错误宏；如果希望保留用户草稿，可以引入 disabled 草稿机制，例如配置字段增加 `enabled: false` 和 `compile_error: "第 3 行: ..."`。运行态编译时跳过 disabled 映射，GUI 中显示“禁用/有错误”状态。目标是：无效宏不会进入可运行映射集合，热更新和启动逻辑不被错误草稿破坏。

## P2：`main.py` CLI 入口已落后于 GUI 维护线

当前 `main.py` 仍是旧式入口，只加载默认配置并直接启动 mapper，然后 sleep 等待 Ctrl+C。它不支持多配置方案，不支持 GUI 中的热更新恢复逻辑，不支持配置读取错误弹窗/提示，不支持运行状态恢复，也不知道新的配置管理能力。现在 README 主要引导源码运行 `gui.py`，而仓库中仍存在一个行为落后的 `main.py`，会增加维护和用户理解成本。建议二选一：第一，明确标注 `main.py` 为 legacy/debug only，不作为正式入口；第二，继续维护 CLI，让它复用 GUI 同一套配置加载/校验逻辑，并支持参数，例如 `--config`、`--target-process`、`--validate-only`。目标是：仓库不要长期存在两个行为不一致的入口，避免用户从 CLI 跑出和 GUI 不同的行为。

## P2：热更新失败恢复旧映射时，旧 trigger state 被全部置 False，可能丢失运行态状态

`_reload_running_mapper()` 热更新前保存 `old_mappings = dict(self.mapper.mappings)`，但 `old_trigger_states` 是用 `{trigger: False for trigger in old_mappings}` 重建的。这样恢复旧映射时，所有触发状态都会被重置为 False。通常问题不大，因为热更新会 stop/start mapper，但如果热更新发生在某个 hold 映射或宏处于临界状态时，状态重置可能掩盖真实按下状态。维护版建议：恢复旧映射时尽量使用旧 `trigger_states` 的快照，而不是全部置 False；或者在热更新前强制 `_release_all()` 并明确把所有触发态归零。目标是：热更新失败恢复逻辑状态语义清晰，不出现“旧映射恢复了但状态不是旧状态”的隐性问题。

## P2：`_sending_depth` 不是线程安全计数，且只过滤 down 事件

`mapper.py` 中 `_send_key()` 会修改 `_sending_depth`，handler 中通过 `if self._sending_depth > 0 and event.event_type != 'up': return True` 试图避免自己发送的输入重新触发 hook。这个计数没有加锁，多个宏线程或 GUI/mapper 线程同时发输入时可能出现竞争。另外当前只在 `event_type != 'up'` 时过滤，也就是 up 事件仍可能进入后续逻辑。维护版建议：给 `_sending_depth` 的读写加锁，或者改成 `threading.local()` / context manager；同时明确为什么只过滤 down，不过滤 up。如果自发送事件可能产生 up 回调，也应统一过滤。目标是：避免 BAKS 自己注入的按键再次被自己的 hook 当作用户输入处理，减少递归触发和状态错乱。

## P2：全局热键注册未随运行中热键修改即时更新

GUI 中捕获热键后会保存配置并提示“下次启动映射时生效”。这是可接受的，但容易让用户误解为立即生效。如果这是设计选择，建议在 UI 文案中明确“当前运行中的热键不变，停止并重新启动映射后生效”。如果希望维护体验更好，可以在 mapper 正在运行时，先 `keyboard.remove_hotkey(old_hotkey)`，再 `keyboard.add_hotkey(new_hotkey, self.toggle_from_hotkey)`，失败时恢复旧热键。目标是：热键设置行为和用户预期一致。

## P2：键捕获对话框使用 `keyboard.hook(..., suppress=True)`，异常关闭时需保证 unhook

`KeyCaptureDialog` 和 `HotkeyCaptureDialog` 现在改为使用 `keyboard.hook(..., suppress=True)` 捕获键盘输入，并在 `stop_listeners()` 中 unhook。这比混用 pynput 键盘监听更统一，但它也意味着捕获窗口打开期间全局键盘输入会被 suppress。需要确保所有关闭路径都调用 `stop_listeners()`，包括正常捕获、取消、窗口销毁、异常、父窗口关闭。当前 `_close()` 和 `_on_cancel()` 都会调用，但如果 `self.top.after(10, self._close)` 之后窗口已被销毁或父窗口关闭，仍可能有异常路径。建议补充防御：`_close()` 中先判断 `self.top.winfo_exists()`；父窗口关闭时如果捕获对话框存在，先显式关闭；以及对 `keyboard.unhook()` 失败记录日志。目标是：捕获对话框不会留下全局 hook，避免关闭窗口后键盘仍被拦截。

## P2：鼠标触发键监听无法 suppress 原始鼠标点击，README 需要继续明确边界

当前鼠标触发使用 `pynput_mouse.Listener(on_click=...)`，它一般不能像 keyboard hook 那样可靠阻止原始鼠标点击继续传递给游戏。README 中已有相关说明，但现在 GUI 也支持鼠标触发、宏拖拽、多配置，建议在 GUI tooltip 或帮助说明中也明确：鼠标触发宏通常不能阻止原始鼠标点击，尤其是左键/右键可能同时被游戏接收。目标是：用户对鼠标触发的行为边界有正确预期，减少“宏触发了但原点击也生效”的误报。

## P3：依赖未固定版本，发布构建不可复现

`requirements.txt` 当前仍未 pin 版本，只写了 `keyboard`、`psutil`、`pynput`、`pyinstaller`。这些依赖和 Windows hook、输入注入、PyInstaller 打包行为强相关，版本漂移可能导致不同机器、不同时期安装后行为不同。维护版建议固定版本，例如 `keyboard==0.13.5`，其余依赖也根据本地验证版本 pin 住；如需开发依赖，可以拆成 `requirements.txt` 和 `requirements-dev.txt`。目标是：发布构建可复现，减少“别人机器能跑、我机器不能跑”以及新版依赖破坏 hook 行为的问题。

## P3：PyInstaller spec 中仍启用 UPX，可能增加杀软误报

`BAKeySmith.spec` 当前使用 `upx=True`。BAKS 本身包含全局键盘 hook、鼠标监听、SendInput、管理员运行提示等敏感行为，UPX 压缩可能进一步增加 Windows Defender 或第三方杀软误报概率。维护版建议发布构建默认改成 `upx=False`，必要时只在本地实验构建中启用 UPX。目标是：降低杀软误报风险，提高用户信任度。

## P3：Windows-only 边界没有集中声明

`utils.py` 和 `gui.py` import 时直接访问 `ctypes.windll.user32`、`imm32` 等 Windows API。作为 Windows-only 工具这是正常的，但如果在非 Windows 环境中导入模块，会直接失败。建议在入口处集中判断 `sys.platform == "win32"`，错误信息明确写出“BA KeySmith only supports Windows”；同时尽量让纯逻辑模块，例如脚本编译器，保持可测试。目标是：平台不匹配时给出清晰错误，而不是 import 阶段抛难懂异常。

## P3：输入注入失败缺少可诊断日志

`send_key_input()` 和 `send_mouse_event()` 失败时主要返回 False，上层 `_send_key()` 也只是返回 False，没有记录失败原因。用户遇到“映射没有生效”时，很难判断是权限问题、目标窗口不在前台、SendInput 失败、键名不支持、游戏过滤输入，还是宏脚本本身问题。维护版建议在 debug/log 模式下记录：key_name、vk、scan code、is_down、SendInput 返回值、`ctypes.GetLastError()`、当前前台进程名、目标进程名、BAKS 是否管理员运行。目标是：维护和用户排查更容易，不靠猜测。

## 建议修复顺序

建议按以下顺序处理，避免在高风险基础未稳时继续扩 GUI 或新增宏指令：第一，验证并修复 `suppress=True` 在非游戏窗口下可能吞键的问题；第二，前台窗口判断去掉 0.3–0.5 秒长缓存，至少在 key down 时实时判断；第三，修复宏 stop flag 生命周期问题，不要在 stop 中提前清空仍活跃线程状态，最好改用 `threading.Event`；第四，修复新建/重命名配置对话框重复 restore 导致状态错乱的问题；第五，增加配置名净化，禁止路径字符、非法文件名字符和 `..`；第六，修复 `wait` 文档与实现不一致，建议支持 float；第七，给宏编辑器语法检查加 debounce；第八，禁止保存语法错误宏，或保存为 disabled 草稿；第九，明确 `main.py` 是 legacy/debug only 还是继续维护的 CLI；第十，pin 依赖版本；第十一，发布版关闭 UPX；第十二，补充 Windows-only 入口提示和输入注入失败日志。

## 总体结论

当前 main 分支已经比之前更像一个可维护的 Python 版 BAKS：前台窗口判断、多配置方案、运行中热更新恢复这些方向都正确。现在剩下的关键不是大改架构，而是把输入安全边界和运行态生命周期补完整。最优先必须确认并解决 `suppress=True` 的真实放行语义；其次是焦点缓存、宏停止、配置对话框恢复、配置名路径安全。修完这些后，Python 维护版可以进入更稳定的维护节奏，再考虑 GUI polish、新宏指令或发布体验优化。
